# Release policy

This page defines the public release-candidate and artifact contract. Apostate
is not published by an arbitrary push. A release is publishable only after the
checks below have passed and the release has been explicitly approved.

## Version boundaries

The initial release uses:

- package version: `0.1.0`
- Chromium version: `152.0.7977.83`
- profile catalogue version: `1`

The Chromium pin is recorded in [`build/CHROMIUM_VERSION`](../build/CHROMIUM_VERSION).
Build inputs and reproducibility rules are described in
[`build/README.md`](../build/README.md) and [`docs/BUILD.md`](BUILD.md).

A package, profile catalogue, or browser build change creates a new immutable
release identity. Existing identities must not silently resolve to new profile
families or binaries.

## Release artifacts

The initial target names are fixed:

```text
apostate-152.0.7977.83-linux-x64.tar.zst
apostate-152.0.7977.83-linux-arm64.tar.zst
apostate-152.0.7977.83-macos-arm64.tar.zst
apostate-152.0.7977.83-windows-x64.zip
```

Each bundle contains the applicable executable or app, licenses and `NOTICE`,
the resolved build manifest, and the profile catalogue version required by the
resolver. Archive names and target labels are part of the package contract;
renaming an archive is a release change.

The build manifest binds the source and build inputs to output hashes. The
checked-in example is [`build/MANIFEST.lock`](../build/MANIFEST.lock), generated
by `scripts/build.sh`; a published release must provide a manifest generated by
the build that produced that artifact.

## Release manifest and signatures

A release publishes an immutable manifest entry for each artifact. Its logical
shape is:

```json
{
  "package_version": "0.1.0",
  "chromium_version": "152.0.7977.83",
  "catalogue_version": 1,
  "platform": "linux-x64",
  "artifact": "apostate-152.0.7977.83-linux-x64.tar.zst",
  "sha256": "...",
  "signature": "...",
  "source_revision": "...",
  "patch_series_sha256": "...",
  "build_manifest_sha256": "..."
}
```

The release signing key, or the adopted Sigstore keyless verification policy,
is published with the release process. Verification rules are stable and
versioned. Official package downloads must:

1. obtain the release manifest before extraction;
2. verify that the artifact name, target, versions, and source/build references
   match the requested release;
3. reject a missing signature;
4. reject an invalid signature or an artifact whose SHA-256 differs from the
   manifest; and
5. extract only after signature verification succeeds.

SHA-256 provides integrity and lookup. It is not a substitute for authenticity
verification. Private signing keys, proxy credentials, licence keys, and other
secrets must never be committed or written to build logs.

## Release-candidate gate

The release-candidate gate is an evidence gate, not a checklist of intended
features. The status below describes the current public baseline and avoids
claiming unverified milestones:

| Area | Status | Required evidence before publication |
| --- | --- | --- |
| Public profile and launch contract | Documented | Keep CLI, Python, Node, schema, and catalogue semantics aligned. |
| Direct CLI seed/persona switches | Not implemented | Add and compile native `--fingerprint` and `--fingerprint-platform` handling; the current native entry point is `--apostate-profile`. |
| Chromium/build pin | Pin present | Independent rebuild reproduces the release output hashes. |
| Profile catalogue and deterministic resolver | Compatibility-backed initial catalogue offered; release evidence pending | Versioned Apostate-owned catalogue, deterministic resolution, schema/coherence checks, and native compatibility acceptance for every offered family. |
| Native process propagation and cross-surface conformance | Not claimed | Actual browser, renderer, GPU, and network process evidence from the release binary. |
| GeoIP, proxy, and WebRTC/network alignment | Not release-ready | Proxy-exit lookup, explicit override precedence, timeout diagnostics, and network coherence evidence. |
| Python package | Not release-ready | Fresh install, cache hit/miss, signature rejection, persistent-context, sync, and async smoke runs. |
| Node package | Not release-ready | ESM import, declarations, cache/signature behavior, and launch smoke runs. |
| Four target builds | Not complete | Successful macOS arm64, Linux arm64, Linux x64, and Windows x64 builds with manifests. |
| Signed artifacts | Not published | Immutable artifacts and manifests independently verified before extraction. |
| Physical V2/V3/V4 and compatibility V3-C/V4-C claims | Not claimed | Do not infer physical or compatibility milestones from compilation, schema validation, a renderer string, or a single detector probe. |

The initial catalogue offer is the set of normalized compatibility-backed
families derived from authorized compatibility captures. They may be selectable
before equivalent physical captures exist, but every unvalidated surface stays
provisional or limited in release reporting. V3-C and V4-C are the acceptance
tracks for native compatibility conformance and compatibility detector results;
they are valid product evidence, but never physical-device T0 evidence.

At this baseline, the presence of a Chromium pin or a generated Linux manifest
does not demonstrate four-runner reproducibility, native process propagation,
WebRTC coherence, package readiness, or physical-device authenticity. Until all
required evidence is recorded, the correct public status is **release-candidate
baseline, not publishable**.

## Required verification

Before an approved publication, the release owner records results for:

- deterministic resolution with the same seed, platform, catalogue, and build;
- changed catalogue or schema versions producing a new identity;
- invalid family, GPU, display, and profile combinations failing before launch;
- explicit locale/timezone overrides taking precedence over GeoIP and profile
  values;
- proxy and direct GeoIP paths resolving the actual observed exit network;
- native values agreeing across browser, renderer, GPU, network, and worker
  paths where the surface is shared;
- stable canvas, text, WebGL, WebGPU, audio, font, and media behavior for the
  supported family claims;
- WebRTC and HTTP/network behavior not contradicting proxy egress;
- direct CLI and package launches producing equivalent native configuration;
- fresh package installation on every supported target;
- corrupted, truncated, unsigned, and incorrectly signed downloads being
  rejected before extraction;
- persistent profile reopen and abnormal process cleanup; and
- an independent rebuild reproducing every hash permitted by the target.

Compatibility checks and detector results are reported as compatibility results.
They do not establish that a generated profile is a separately measured
physical computer.

## Publication rule

Do not publish, push, tag, or create a release from this baseline. Publication
requires the complete evidence set, a reviewed immutable manifest, verified
signatures, and explicit approval for the release.
